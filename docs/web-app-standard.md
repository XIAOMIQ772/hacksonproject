# Web 应用编码规范

本规范约束 agent 根据需求文档生成的 Web 应用。目标是：应用的每项功能都能通过浏览器自动化测试，按角色和名称定位控件，用点击、输入、按键、粘贴、拖拽、上传完成操作并验证结果。

## 0. 适用范围与优先级

- 0.1 需求文档与本规范冲突时，以需求文档为准。需求明确指定元素类型、角色、文案、交互方式时，严格照做。
- 0.2 需求未规定的实现细节，按本规范执行。
- 0.3 “必须”表示违反即判定不合格；“应”表示默认遵守，有明确理由时可偏离，并在代码中注释理由。

## 1. 需求解读

- 1.1 需求描述是验收依据。场景步骤与描述不一致或只含占位内容时，以描述为准。
- 1.2 描述与场景存在矛盾时，实现应同时满足两种解读。例如，一处写“必须显示确认对话框”，另一处写“如出现确认对话框”，应显示对话框，且对话框的确认按钮名称与需求一致。
- 1.3 需求中加引号的界面文字是控件的无障碍名称，必须逐字使用，包括大小写、空格和标点。
- 1.4 需求中的错误提示、状态文案必须逐字使用。含占位符的文案（如 `<cell coordinate>`）按实际值替换，其余部分不变。

验证：从需求中抽取全部加引号的字符串，逐条在运行中的页面上按“角色 + 名称”查找，每条至少命中一个可见元素。

## 2. 语义与无障碍

- 2.1 需求为控件指定了角色（链接、按钮、标题、标签页、菜单项等）时，必须使用该角色。
- 2.2 未指定角色时，按行为选择：跳转页面用链接（带 `href` 的 `<a>`），执行操作用按钮（`<button>`）。
- 2.3 每个可交互控件必须有无障碍名称：按钮和链接用可见文字；输入框用关联的 `<label>`；只有图标的控件用 `aria-label`。
- 2.4 同一视图内，同一角色的控件名称必须唯一。重复出现的同类元素（列表行、表格单元格）用包含标识的名称区分，如 `Open dropdown for B2`。
- 2.5 每个标签文字只能关联一个元素。复合控件的弹出部分（listbox、menu）不得复用触发元素的 `aria-labelledby` 或同名 `aria-label`，否则按标签查找会同时命中两个元素。
- 2.6 页面主体和对话框必须有标题元素，标题文字与需求一致。
- 2.7 状态变化必须体现在无障碍属性上：选中用 `aria-selected`，展开用 `aria-expanded`，禁用用 `disabled` 或 `aria-disabled`，当前项用 `aria-current`。

验证：用 Playwright 读取每个页面的无障碍树，检查以下三项：
- 所有可交互元素都有名称；
- 同一视图内没有重名的同角色元素；
- 每个 `<label>` 文字按标签查找只命中一个元素；
- 需求点名的角色全部存在。

## 3. 组件

- 3.1 简单控件使用原生 HTML 元素：按钮、链接、文本框、多行文本框、复选框、单选框、文件选择框。
- 3.2 复合控件必须自行实现，弹出内容渲染在页面 DOM 中，结构和键盘交互遵循 WAI-ARIA Authoring Practices。

| 控件 | 结构 |
| --- | --- |
| 下拉选择 | `role=combobox` 的触发元素，名称来自标签；点击后显示 `role=listbox`，其中每项为可见、可点击的 `role=option`，名称为选项文字 |
| 菜单 | 触发按钮，带 `aria-haspopup` 和 `aria-expanded`；点击后显示 `role=menu`，其中每项为 `role=menuitem` |
| 对话框 | `role=dialog`，`aria-labelledby` 指向标题；打开时焦点移入，关闭后焦点返回触发元素 |
| 标签页 | `role=tablist`，其中每项为 `role=tab`，当前项带 `aria-selected=true` |
| 数据表格 | 可编辑表格用 `role=grid`，单元格用 `role=gridcell`，需求规定了单元格名称时用 `aria-label` 设置 |

- 3.3 除非需求明确指定，否则不使用原生下拉列表（`<select>`）、原生日期和颜色选择器，以及 `alert`、`confirm`、`prompt`。这些控件的弹出内容由浏览器绘制，不在页面 DOM 中，无法统一样式和测试。
- 3.4 同一功能提供多个入口时，每个入口都必须可用。需求提到右键菜单、标签页菜单等入口时，必须同时提供一个可见的、带名称的按钮来打开同一菜单。
- 3.5 复合控件应抽成共用组件，全应用复用同一实现。

验证：
- 静态检查：源码中不出现 `<select`、`type="date"`、`type="color"`，也不调用 `alert(`、`confirm(`、`prompt(`。需求点名要求的除外，并在代码中注明对应的需求编号。
- 运行检查：逐个点击页面上的 combobox 和菜单按钮，确认出现可见的 option 或 menuitem；点击任一项后，弹出内容关闭，值随之更新。

## 4. 交互

- 4.1 所有操作必须能用鼠标点击完成，不依赖悬停才出现的入口。
- 4.2 文本输入：Enter 提交，Escape 取消并恢复原值；输入框失去焦点时提交，需求另有规定的除外。
- 4.3 需求提到的快捷键必须实现，并在输入框和表格获得焦点时都生效。
- 4.4 复制、剪切、粘贴必须处理浏览器的 `copy`、`cut`、`paste` 事件，读写系统剪贴板的纯文本。二维数据使用制表符分隔列、换行分隔行。剪切后粘贴的语义是移动：粘贴成功后清空源位置。
- 4.5 拖拽选择必须响应 `mousedown`、`mousemove`、`mouseup` 事件序列。
- 4.6 文件上传使用带标签的 `<input type="file">`。文件下载用 Blob 生成内容，通过带 `download` 属性的链接触发，文件名和编码符合需求。
- 4.7 界面不使用动画和过渡效果。操作完成后，界面立即反映结果，不使用骨架屏或延迟渲染。

验证：为每个交互写端到端测试，只使用 `getByRole`/`getByLabel` 定位，只使用点击、填写、按键、粘贴、拖拽、上传操作。

## 5. 数据与持久化

- 5.1 所有业务数据保存在服务端数据库，不以浏览器本地存储作为唯一存储。
- 5.2 需求规定需要保留的界面状态（当前页签、选区、筛选条件、排序等），与业务数据一起保存在服务端。
- 5.3 每次修改必须在操作完成时立即写入服务端，不做延时合并，不等页面卸载时再保存。连续写入按先后顺序生效，后发出的写入不能被先发出的覆盖。
- 5.4 每个业务对象有稳定的 URL。在新的浏览器会话中直接访问该 URL，必须显示对象的最新状态。
- 5.5 刷新页面后，页面必须恢复到刷新前已成功保存的状态。
- 5.6 名称、数值等用户输入按原样保存和显示，支持任意长度和特殊字符，不依赖名称格式判断行为。
- 5.7 数据库中可能同时存在大量其他记录。新建或修改的对象必须能在对应列表中直接看到，不因分页、排序或数量上限被隐藏。
- 5.8 撤销、重做等操作历史按业务对象隔离，一个对象上的撤销不能影响另一个对象。

验证：
- 每个端到端测试在最后一步操作后刷新页面，再次断言结果。
- 另开一个浏览器上下文，直接访问对象 URL 并断言。
- 测试开始前向数据库写入 50 条无关记录，检查列表可见性不受影响。

## 6. 校验与错误处理

- 6.1 输入校验在服务端执行；前端可以提前校验，但不能替代服务端校验。
- 6.2 校验失败时，数据不变：
  - 不写入任何部分结果；
  - 原有的值和名称保持显示；
  - 输入框保留用户输入，便于修改。
- 6.3 批量操作中任一目标校验失败，整个操作都不生效。
- 6.4 错误提示显示在对应控件旁，使用 `role=alert`，文字与需求一致。对应输入框设置 `aria-invalid=true`，并用 `aria-describedby` 指向错误提示。
- 6.5 同一错误在页面上只显示一处，不同时使用弹出提示和行内提示。
- 6.6 服务端错误以 JSON 返回，前端显示错误信息，页面不崩溃，不停留在加载状态。

验证：对每条需求中的错误文案，编写一个触发该错误的测试，断言提示文字可见、原数据未变，并在刷新后再次断言。

## 7. 数据初始化

- 7.1 需求描述的预置数据（账号、示例记录等）必须在应用首次启动时自动写入。在无数据库文件的全新环境中执行启动命令后，预置数据即可使用。
- 7.2 初始化可重复执行：再次启动时不重复插入，不覆盖用户已修改的数据。
- 7.3 需求中多处预置数据互相冲突时，优先保证每处都能通过新建对象的流程完成操作；预置数据按需求中出现最多的版本准备。

验证：删除数据库文件，按交付命令构建并启动，用需求中的账号和记录名称执行一次登录或打开操作。

## 8. 实现范围与样式

- 8.1 只实现需求描述的页面、控件和文案，不添加需求之外的功能入口。
- 8.2 样式只满足以下条件：
  - 元素可见，尺寸不为零；
  - 可点击区域不被其他元素遮挡；
  - 布局与需求中的参考图一致；
  - 表格按行列排列。

  不写装饰性样式，不引入 UI 组件库。
- 8.3 弹出层关闭后不遗留遮罩；弹出层打开时，不遮挡需求要求同时可见的元素。
- 8.4 依赖仅限模板已有的包。确需新增时，只使用纯 JavaScript 包，不使用需要本地编译的包。

验证：用 Playwright 对需求点名的每个控件执行 `toBeVisible` 断言，并执行一次不带 `force` 的点击。

## 9. 交付

- 9.1 输出目录包含 `frontend/` 和 `backend/`。在全新环境中按以下顺序执行命令即可运行：

  ```sh
  cd frontend && npm install && npm run build
  cd ../backend && npm install && npm start
  ```

- 9.2 后端通过环境变量 `PORT` 监听端口，同时提供 `/api/*` 接口和前端构建产物。
- 9.3 交付前必须完成以下检查：
  - 构建成功；
  - 删除数据库后冷启动成功；
  - 第 1–8 节的全部验证通过。
- 9.4 未完成的功能保持页面可用：不渲染不可用的控件，不因缺失功能导致页面报错。
